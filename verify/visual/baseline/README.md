# verify/visual/baseline/ · 视觉回归图库（映射表）

> **这一份图库是"基准"，不是"证据截图"。** 它由**真实交付物**（`index.html`，走 HTTP）在**钉死的视口**下抓出，
> 供 `verify/visual/visual.js compare` 逐像素比对。图库一经验收即**冻结**（改它 = 改变基准，必须写清归因）。
>
> **当前图库批次 = 第 2 批（2026-10-09）**：钉相位容差从 ±8 收到 **±4** 并**三张一起重抓**（原因见 §2.1，被取代的旧 md5 也记在那里）。
>
> 抓图命令（可完整重跑，`--tol 4` 就是本批的容差）：
> ```bash
> # 前置：预览服务在跑（受管后台作业，别重复启动）
> python3 -m http.server 5173 --bind 127.0.0.1
> # 抓图 → 比对（--out 指向**临时目录**；图库目录本身不放抓图产物）
> node template/verify/visual/visual.js shoot   --tol 4 --out /tmp/base-r2
> node template/verify/visual/visual.js compare --baseline template/verify/visual/baseline --actual /tmp/base-r2
> ```

## 2. 比对口径（判定唯一的入口在 `visual.js` 的 `judge()`）

| 参数 | 默认 | 含义 |
|---|---|---|
| `maxDiff` | **8** | 逐通道容差。|Δ| ≤ 8 的像素**不算差异**；> 8 记 1 个"超容差像素"（**±8 不算、±9 算**，边界由 `visual-gate.js` 断言钉死） |
| `maxRatio` | **0.2%** | 超容差像素占比阈值；超过即判"不一致" |

判定输出三件事：**差异计数**（超容差像素个数，门禁比的就是这一个数）、**差异图**（红点 = 超容差像素，其余压暗灰）、
**人可读结论**（一行 `✓ 一致 / ✗ 不一致`，带计数、比例、最大通道差）。尺寸不一致**直接判失败**（先查钉视口，不要调容差）。

### 噪声包络（实测，**当前批次 = 2026-10-09 第 2 批**，`--tol 4`）

同一份 `index.html`、同一台机器、同一条命令重跑，仍会有**亚像素级**的非确定性。
它的来源已实测**定位**：差异像素的包围盒**恰好是方块本体**（1200 那张 127×126、375 那张 64×63、destroyed 那张 15×10 是球），
即噪声 = **"方块/球没落在同一个设备像素上"**，不是别处漂移。

6 次重跑实测（`maxDiff=8` 下的超容差像素数）：

| 图 | 重跑间差异（实测） | 占比 |
|---|---|---|
| `ready-square-center-1200x760.png` | 0 / 0 / 381 / 381 / 381 / 381 像素 | 0 ~ **0.042%** |
| `ready-square-center-375x600.png` | 0 / 0 / 128 / 128 / 128 / 128 像素 | 0 ~ **0.057%** |
| `destroyed-after-explosion-1200x760.png` | 340 / 340 / 340 / 340 / 340 / 340 像素 | 0.037% |

**真回归有多大**（实测对照）：把 `ready-square-center-1200x760.png` 与 `verify/card-07/` 里"方块扫到别处"的旧图比 →
**6223 像素 = 0.682%**；窄窗那张 **4096 像素 = 1.820%**。
→ 噪声（≤0.057%）与真回归（≥0.68%）之间差**一个数量级**，故 `maxRatio` 取 **0.2%**：约 **3.5×** 噪声余量、约 3.4× 低于最小可辨回归。

> 想更严：`--max-ratio 0.001`（0.1%）—— 仍高于噪声（0.057%），但余量只剩 1.75×。
> `--max-ratio 0`（任何超容差像素都判失败）在本机噪声下**会误报**，除非先把"钉相位"做得更死。
> 想更松：别调容差，先问"这一条验收还值不值得自动判"。

### 2.1 第 2 批重建的归因（**有意取代，不是回归**）

**谁取代了谁**：2026-10-09 重建的 3 张图（本节 §1 的 md5）取代了 2026-10-08 第 1 批的 3 张图：

| 图 | 第 1 批 md5（**已废弃**） | 第 2 批 md5（当前） |
|---|---|---|
| `ready-square-center-1200x760.png` | `f95845a554f4fed3e1289d8d3ea4e511` | `7047fef40299417011f7efa526da2921` |
| `ready-square-center-375x600.png` | `5d703730f833fcc7fd397e3c05cedc7c` | `de2c399019e4de4ecfbada4d9b32de5a` |
| `destroyed-after-explosion-1200x760.png` | `5eb4da3ddff2c594373dcd082cbb0efc` | `270de9e3f61bb2edd31e9be1b95960e4` |

**为什么换**：第 1 批窄窗那张的钉相位容差是 **±8 世界 px**（宽窗 ±6）。复核时实测到一次 **0.112%** 的重跑差异
（差异包围盒 = 方块本体 64×63）——窄窗 `viewScale≈0.6`，±8 世界 px ≈ ±4.8 设备 px，方块整体平移 1~2 px 就吃掉了阈值 0.2% 的 **56%**（余量只剩 1.8×，太薄）。
处置：三张**统一**把钉相位容差收到 **±4 世界 px**（≈2.4 设备 px）并**整批重抓**，噪声最坏值从 0.112% → **0.057%**，余量回到 3.5×。

**为什么整批重抓**：图库内部若混着不同批次（不同 `--tol`、不同会话），比对口径就不一致；
"一批一次抓齐"是可复核的最小代价。因此本次 3 张的 md5 **全都变了**，即使其中 2 张的容差其实没改。

**旧图在哪**：第 1 批的 3 张 PNG 保存在 `rescue/paused-sessions-20261008`（抢救分支，不推不合并），
取回方式：`git show rescue/paused-sessions-20261008:template/verify/visual/baseline/<文件名> > /tmp/<文件名>`。**本目录只加不改**，不保留双份图。

## 4. 边界（原理层，必须写在人看得见的地方）

1. **像素比对只能抓"意外变化"，抓不了"符合预期但依然荒谬"。**
   例：橡皮筋跟着球跑（卡 02 的坑）—— 如果它从第一版就是这样，baseline 就长这样，比对永远通过。
   所以：`✓ 一致` 的含义只是"和上次看到的一样"，**不等于"对"**。
2. **人的视觉判断不可被替代，只能被缩小到"看哪几张图"。**
   本环节把人的工作从"每张卡看 5 张图、找不同"缩小成"**门禁失败时，看差异图上的红点**"；
   凡是"好看不好看 / 像不像"的判断，仍然只能人做（判定分工见 `verify/README.md`）。
3. **不做像素比对的场合**：任何"预期之内就该变"的改动（换配色、调速度、加元素）都会让比对失败 ——
   这时正确动作是**更新基准并写明归因**，而不是调容差把红点吞掉。
