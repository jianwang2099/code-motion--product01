# 任务卡模板（TASK CARD TEMPLATE）

> **本文件是模板；项目特定段落用 <尖括号> 标注。**
> 骨架里的字段是**通用形状**（含一个"画面/参数"类字段作为示例），按你项目的形态替换字段名与示例。
>
> 导演产出任务卡时**复制本骨架并逐项填写**；空缺项写「无」或「由实现者决定」，不要删行。
> 卡必须是**自足**的：Worker 看不到导演的对话，卡里没写的它一律不知道。

---

```markdown
## 任务卡 <编号>

### 目标
<一句话说清这一卡要达成什么。不要写"优化一下"这种无法验收的话。>

### 验收标准
1. <可观测、可自证的标准>
2. <…>
（每条都要能被 Worker 用代码或命令给出证据；不要写"感觉更流畅"。）

### 涉及文件
- <相对路径> — <新建 / 修改 / 只读参考>

### 画面与时间轴
<这是「领域特定参数」的一个示例字段（适用于视觉/时序类项目）：按你项目的形态替换字段名。
若你的项目没有"画面"，改成对应形态的参数段，例如：接口契约 / 数据模型 / 性能预算 / 交互时序。>

- 总时长：<秒>
- 关键节点：<0.0s 起点 → 0.4s 中间态 → 0.8s 结束，逐段写>
- 循环 / 单次：<循环播放 / 播放一次>

### 动效参数
<同上：领域特定参数的第二个示例字段。能给具体数字就给数字——模糊描述无法验收。>

- 缓动：<linear / easeInOut / 自定义曲线>
- 关键数值：<各参数的基准值、系数、容差……>
- 视觉：<颜色、大小、透明度、拖尾等>

### 技术约束
- <必须使用的库 / 必须保持的写法 / 性能要求 / 不许引入依赖>
- <运行环境要求（运行时版本、分辨率、浏览器等）>

### 不许改动的部分
- <本卡范围外、禁止触碰的文件>
- 注意：**不要写成「不许新建任何文件」**，那会把验证证据一起禁掉（见下方「验证证据出口」）。

### 验证证据出口
- 实现文件：<交付物文件路径> — 可改
- 证据目录：`verify/card-<编号>/` — **唯一允许新建文件的地方**
- 其他一切：不得触碰

### 预览端口
<默认 5173；若需指定则写明>
```

## 验证证据出口（重要，别省这一段）

**教训来源**：**曾有一个项目**，某张卡写了「不许新建任何文件」，Worker 只能把自检脚本和截图扔进 `/tmp`，交付时全部消失，导演**无法独立复核**——在流程上等于没验证。

所以每张实现卡都要显式留出口，三段式写死：

| 范围 | 权限 |
|---|---|
| 实现文件（项目自己的交付物，路径由卡指定） | 可改 |
| `verify/card-<编号>/` | **可新建**（唯一出口） |
| 其他一切 | 不得触碰 |

`verify/card-<编号>/` 里应至少包含：

1. **自检脚本** —— 可从固定路径重跑，退出码 0 = 全通过
2. **证据截图** —— 文件名自解释，并在 README 里标注「这张图证明哪条验收标准」+ **实际视口尺寸**
3. **README.md** —— 命令级复现步骤，让导演能自己跑一遍

> 判据：**如果导演不能独立重跑一遍，这份"验证"就不算数。**

### 已知坑（实测，省你一次 debug）

- 无头浏览器（如 headless Edge）的 `--window-size=1200,760` **实测只给到 1192×629**（被浏览器 UI 裁掉），窄窗还有最小宽度（要 375 会被撑成 492×509）。
- 正确做法：用 CDP 的 `Emulation.setDeviceMetricsOverride` 把视口钉死；README 里标注的尺寸要用页面内 `window.innerWidth/Height` 的**实测值**，不是命令行参数。
- 截图脚本应驱动**真实页面**（不复制、不注入），否则截图证明的不是交付物本身。
- （上面这组数字是踩坑项目的实测值，换环境要自己重测——**别照抄别人的数字**。）

## 填写要求（导演自检清单）

发卡前逐条确认：

- [ ] **自足**：Worker 只看这张卡 + 角色卡，能不能不动脑子地问出必要信息？缺什么补什么。
- [ ] **可验收**：每条验收标准都能被 Worker 用代码或命令给出证据。
- [ ] **可执行**：没有"优化一下""更好看"这类无法落地的表述。
- [ ] **有边界**：「不许改动的部分」写清了，避免它顺手重构。
- [ ] **有证据出口**：`verify/card-<编号>/` 已写明，且没写"不许新建任何文件"。
- [ ] **有增量说明**：若是续派卡，明确写出「基于上一轮，只改 X」。
- [ ] **给了端口**：预览端口明确，避免和已有服务冲突。
- [ ] **无自相矛盾**：卡内所有约束互不打架（见下方「一致性检查」）。
- [ ] **断言是黑盒的**：验收标准不绑定 Worker 自己要新引入的内部变量。
- [ ] **视觉决策已交给人**：视觉表现至少要给 A/B 选项，不替人拍板。

## 一致性检查（两次返工的教训都出在这里）

**已发生的两次返工，根因完全相同：导演在卡里写了自相矛盾的约束。**
（**曾有一个项目**连续两张卡都栽在这里——下表是它的复盘，已做匿名化。换项目后请换成你自己的案例。）

| 事故 | 矛盾的约束 | 后果 |
|---|---|---|
| 某卡 | 一边要求"给出渲染证据"，一边禁止"新建任何文件" | 证据只能扔 `/tmp`，交付后消失，**无法复核** |
| 某卡 | 一边沿用上一张卡"某元素发射后回到静止形态"，一边要求"整个过程该元素都跟随另一物体的位置" | 出现"有只看不见的手在拽着它追"的**荒诞画面**（物理上互斥） |

**发卡前必须逐条对照的检查**：

1. **新指令 vs 历史裁定** —— 本卡有没有哪条**否定了上一张卡已验收的行为**？
   有的话必须显式写出"本卡改变第 N 张卡的第 M 条"，不能默默覆盖。
2. **视觉指令 vs 物理常识** —— 每个渲染指令问一句：**"这在现实里可能吗？有谁在施力？"**
   某元素跟不跟随另一物体，取决于**有没有东西在拉它**——这类语义要写清，不能只说"跟着它"。
3. **验收标准 vs 实现自由** —— 断言不要建立在"Worker 将要新引入的变量"上。
   ❌ `state` 由 `phaseA` 变为 `phaseB`（它自己刚定义的状态机）
   ✅ 静止后，该物体开始向起点移动（可观测行为）
4. **要求 vs 能力** —— 要求它的东西，它有没有权限/工具做到？（授权范围要覆盖要求）
5. **涉及文件 vs 验收标准** —— "涉及文件"里列的东西，验收标准里有没有兜住？
   否则 Worker 可能不产出，且不算失败。

> **判据：把卡读成一个"没看过上一轮的人"——他能发现哪两条要求互相打架吗？**

## 视觉决策必须交给人

导演**不得自行决定视觉表现**（几何形状、动画形式、配色、镜头感）。这些是人拍板的东西。

### 正确做法分三步，缺一不可

```
① 你列出带取舍说明的 A/B 方案
② 人做出选择
③ 你把「完整任务卡」贴出来，等人确认下发 ← 第 1.5 节的闸门，不可跳过
```

```
### 视觉方案（请你选）
- **方案 A**：<描述> — 优点 <…>；代价 <…>；可调项 <尺寸/配色/姿态…>
- **方案 B**：<描述> — 优点 <…>；代价 <…>
（我推荐 A，因为 <…>）
```

### ⚠️ 最容易搞错的一点：人的方案选择 ≠ 下发授权

**人选了方案 A，只授权了"A 这个方向"，没有授权整张卡。**

卡里的验收标准、边界、证据出口、时长参数，人**都还没看过**。所以：

- ✅ 人选定方案后 → 你据此写完卡 → **贴出来等人确认**
- ❌ 人选定方案后 → 你直接 `subagent(...)` 下发

> **已发生的事故**：导演给 A/B → 人选 A → 导演**立刻下发**。
> 结果卡里有一条**恒真的验收标准**（Worker 什么都不做也能通过）、还**夹带了一个全新的子系统**
> 这个卡外功能、两处视觉语义的冲突也没确认——**这些人都没机会看到，因为它们是在"人选 A"之后才写进卡的。**

原因：视觉要求**无法用约束语言完整表达**。导演自作主张写下的视觉指令，Worker 只会精确执行——
**精确地错**。等你看到画面才发现，已经烧掉一整轮。

> 某卡的事故链条：导演自行选定"某种回到起点的运动方式" → 卡里顺手写下"某元素全程跟随另一物体" →
> Worker 照做 → 人看到荒诞画面。**源头是导演没交出选择权。**

## 一张卡只做一件事（原子性）

**每张卡只允许一个「可独立验收」的目标。**

夹带进来的东西要拆成独立的新卡：

| 夹带物 | 例子 | 为什么必须拆 |
|---|---|---|
| 新的子系统 | 「顺手加个运动过程可视化」——采样 + 数百点对象池 + 逐点材质透明度 + 淡出 + resize | 出问题时**无法定位是哪一半**导致 |
| 新的交互维度 | 「顺带支持滚轮缩放」 | 验收标准互相干扰，失败原因被掩盖 |
| 与目标无关的重构 | 「顺便把渲染循环整理一下」 | 破坏了"增量修改"的可回滚性 |

**判据**：如果这一卡失败了，你能不能一句话说清"失败的是哪个功能"？**说不清就是不原子。**

> **已发生的事故**：**曾有一个项目**，某卡的目标是"修复某个视觉表现"（纯视觉修复），
> 却夹带了"新增一套运动过程的可视化"（一个全新子系统，自带 2 条验收标准）。
> 一旦失败，无法判断是原有视觉部分错了还是新子系统错了。

## 续派（修订）卡的写法

续派时**不重发整张卡**，用这个精简结构：

```markdown
## 修订卡 <编号>

基于你上一轮的成果，只改以下内容：

### 先解除/调整的约束
- <本轮临时放开或收紧哪条边界，写清范围>

### 改动点
1. <具体改什么>
2. <…>

### 保持不动
- <上一轮已通过、本轮不许动的部分>

### 对上一轮「未决问题」的裁定
- <逐条明确回答：维持 / 改 / 否。不置可否会让它下一轮重新猜>

### 新增验收标准
1. <…>（原有的验收标准仍然有效）
```
