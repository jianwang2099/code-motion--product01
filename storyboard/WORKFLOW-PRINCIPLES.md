## 一、四大核心角色

| 角色 | 是什么 | 关键性质 |
|---|---|---|
| **Harness** | 底座/车间 | 无智能。负责调度、插件执行、文件管理、会话隔离、工具调用解析 |
| **Worker** | 岗位智能体 | = 固定角色提示词 + 权限 + 绑定模型 + **独立会话** |
| **Model** | 大脑 | 纯推理。只收文本、只返文本。**没有记忆、没有文件权限、没有工具能力** |
| **Session** | 记事本 | 单个 Worker 的独立记忆空间，隔离上下文，防止上下文爆炸 |

**一句话**：Harness=流水线 · Worker=岗位工人 · Model=工人大脑 · Session=工人专属记事本

> ⚠️ 最容易混淆的一点：**Model 本身没有工具能力**。所有落地操作（读文件、写代码、跑命令）都是 Harness 解析模型输出后驱动插件完成的。理解这个，才能理解为什么"权限"是 Harness 层面的东西，而不是"提示词里让模型别做"。

## 二、机制实测（DSH 实际行为）

这一节全部是**本机真跑**的结果，不是推测。**【实测】**

### 派生与寻址

| 项目 | 实际行为 |
|---|---|
| 派生返回 | `started subagent <uuid>` —— 这个 uuid 就是后续寻址用的 id，也是结算通知里的 `<child-id>` |
| 会话隔离 | Worker **看不到**父会话的任何对话。它只看到启动 prompt 里的内容 |
| 工作目录 | **继承**父会话的 cwd |
| 沙箱/权限 | **继承**父会话的 sandbox override；approval 策略被钉死为 `never` |
| 权限可变性 | **派生瞬间冻结，会话内无法提权**（Worker 自报原文见下） |

Worker 自报的权限原文：

> *"my scope was fixed at delegation time by the parent session's runtime context (workspace-write sandbox rooted at the session workspace, approvals disabled), and cannot be widened from inside this session."*

### 回传

一轮结束时，导演收到一条**用户角色**的独立消息：

```
Background subagent 705fd7df-59bd-4037-87e3-8143b34fce0d finished and will do no further work unless you send it more.

Its closing message:
<Worker 的收尾文本>
```

**关键认知：回来的只有两样** —— 通知头 + 收尾文本。**Worker 的中间推理、读过的文件、试错过程，全部留在它自己的会话里，不会回到导演。**

> 这就是为什么收尾格式必须钉死成固定几段（见 [WORKER-PROTOCOL.md](WORKER-PROTOCOL.md) 第 5 节）——**那是唯一的回传信道**，格式松一点，导演就瞎一半。

### 续派

| 操作 | 实际行为 |
|---|---|
| `send_message(<id>, msg)` | ✅ 对**已结算（idle）**的 Worker 同样有效 |
| 上下文保留 | ✅ 它**保留自己上一轮的上下文**（实测：正确答出首轮的问题） |
| 循环 | 续派后会产生新的结算通知 → 循环可无限延续，不需重新派生 |

### 权限继承的硬约束【代码 + 实测】

- 子 Worker 的权限**永远不可能比父会话宽**
- `approval` 被钉死 `never` → **任何需要审批的操作会被自动拒绝**，不会弹给人
- 推论（**这是自动流转最重要的设计约束**）：

> **`read-only` 的父会话 → 派生出的 Worker 也是 read-only → 写不了代码 → 自动流转直接废掉。**

所以 **「硬锁导演」与「自动流转」在 DSH 里互斥**，必须二选一：

| 目标 | 做法 | 代价 |
|---|---|---|
| 导演**硬锁**不能写代码 | 导演会话用 `read-only` | 只能手动接力；且 `read-only` **创建后不可改**，想切换必须新开会话 |
| **自动流转** | 导演会话用 `workspace-write`，"不写代码"降级为提示词契约 | 约束会漂移，需要靠协议纪律 |

## 三、核心原理

### 原理 1 · 职责分离靠边界，不靠提示词

- **提示词**决定它**想不想**做 → 会漂移、会自我说服
- **沙箱/权限**决定它**能不能**做 → 不会漂移

> **能硬就别软。** 当硬约束与自动流转冲突时，清楚自己在放弃什么，不要以为写了"禁止"就真的禁止了。

### 原理 2 · Session 隔离 = 上下文隔离，不是文件隔离【实测】

| | 是否共享 |
|---|---|
| 工作区文件 | ✅ **共享**，改动立刻可见 |
| 沙箱/权限 | ⬇️ 继承（且只能更窄） |
| 工作目录 | ⬇️ 继承 |
| **对话历史** | ❌ **完全隔离** |

推论：**跨会话唯一信道 = prompt / 任务卡 / 文件**。任何不落盘、不塞进消息的信息，就传不过去。

### 原理 3 · 自动流转 = 工具能力 × 协议纪律

Harness **没有**"导演"这个概念，**没有**"自动接力"这个开关。它只给了三个工具：

```
subagent(prompt, run_in_background)   → 派生独立会话干活
send_message(id, msg)                 → 唤醒它继续干
interrupt_agent(id) / list_agents()   → 打断 / 查看
```

**把它们串成环路的，是导演会话里的角色卡。** 没有协议，工具还在，但没人知道该"派生 → 等通知 → 判验收 → 续派"。

> 所以协议文件**不是文档，是运行时的一部分**。

### 原理 4 · 验收要的是「可重算的数字」，不是描述性语言

| 弱证据（别信） | 强证据（可审计） |
|---|---|
| "动画很流畅" | 可复算的数值序列（例：反弹峰值 `[286.3, 160.4, 92.6, …]`，相邻比值 ≈0.58） |
| "该生效的机制生效了" | 对采样点做最小二乘拟合得到的参数（例：竖直加速度 `−1245 px/s²`），与代码常量对得上 |
| "边界情况都处理了" | 分类计数（例：触边计数 左=2 右=1 上=1 下=21） |
| "应该没问题" | 交付物指纹 `md5`（导演自己算一遍，逐字一致） |

> **规律：能重算的数字 > 描述性语言。** "应该可以""理论上"这两个词标志着证据链断了——这也是 Worker 协议明令禁止它们的原因。

### 原理 5 · 验证证据必须是「可持久审计的交付物」

**【教训】曾有一张卡写了「不许新建任何文件」**，Worker 只能把自检脚本和截图扔进 `/tmp`。交付时全部消失，导演**无法复核一个已经消失的证据链**——在流程上等于没验证。

**这是导演的任务卡设计缺陷，不是 Worker 的问题。**

修正：每张实现卡显式留证据出口，三段式写死：

| 范围 | 权限 |
|---|---|
| 实现文件（项目自己的交付物，路径由卡指定） | 可改 |
| `verify/card-<编号>/` | **可新建**（唯一出口） |
| 其他一切 | 不得触碰 |

> **判据：如果导演不能独立重跑一遍，这份"验证"就不算数。**

### 原理 6 · 验证证据有「时效性」

**【教训】** Worker 交付时报告 `curl` 返回 200 **是真的**——那一刻服务确实活着。但它用 `(cmd &)` 起了个游离进程，父 shell 一结束就被回收。人打开 URL 时看到 `ERR_CONNECTION_REFUSED`（浏览器报 `-102`）。

> **任何验证都只在被观测的那一刻成立。** 导演拿到的是"历史上的 200"，不是"现在的 200"。

两个动作：

1. **导演验收时自己重跑一遍**，不读 Worker 的报告结论（这不是不信任，是流程要求）
2. 长驻服务**必须用受管后台作业启动**，不能用游离进程

### 原理 7 · 验收方法是导演的责任，Worker 只负责执行

**【教训】** 同一张卡里，导演一边要求"给出渲染证据"，一边禁止"新建文件"——**方法被约束掐死了**，Worker 只能退到 `/tmp`。

> 任务卡里出现自相矛盾的约束，责任在导演。Worker 没有权限改需求，它只能硬扛，然后在「未决问题」里报告——**而能读懂那条报告，是导演的功课。**

### 原理 8 · 导演的上下文是稀缺资源

- **导演上下文**：只有「任务卡 + 结算通知 + 判断」→ 保持精简
- **Worker 上下文**：代码、试错、调试全在它那儿 → 不污染导演
- **代价**：结算通知会在导演上下文里**累积**。跑几十轮后，导演也该换新会话，靠协议 + 台账冷启动

> 这就是多 Agent 架构真正省的东西：**不是省 token，是防止单会话上下文爆炸、思维混乱。**

### 原理 9 · 任务卡的一致性由导演负责，且必须显式检查

**【教训·两次返工，根因完全相同：卡内约束自相矛盾】**

**曾有一个项目**连续两张卡都栽在这里，下表是它的复盘（已匿名化）：

| 事故 | 矛盾的约束 | 后果 |
|---|---|---|
| 某卡 | 要求"给出渲染证据" + 禁止"新建任何文件" | 证据只能扔 `/tmp`，交付后消失，无法复核 |
| 某卡 | 沿用上一张卡"某元素发射后回到静止形态" + 要求"整个过程该元素都跟随另一物体的位置" | 出现"有只看不见的手在拽着它追"的荒诞画面（物理上不可能同时成立） |

**Worker 两次都没有错——它精确执行了一张自相矛盾的卡。** 精确地错。

发卡前必须逐条对照：

1. **新指令 vs 历史裁定** —— 有没有否定上一张卡已验收的行为？要显式写出"本卡改变第 N 张卡的第 M 条"，不能默默覆盖。
2. **视觉指令 vs 物理常识** —— 每个渲染指令问一句：**"这在现实里可能吗？有谁在施力？"**
   （某元素跟不跟随另一物体，取决于有没有东西在拉它——这类语义必须写清，不能只说"跟着它"。）
3. **验收标准 vs 实现自由** —— 断言不要建立在 Worker 将要新引入的变量上（否则是拿它自己刚写的东西验它自己）。
4. **要求 vs 能力** —— 要求它的东西，它有没有权限/工具做到？
5. **涉及文件 vs 验收标准** —— 列在"涉及文件"里的东西，验收标准有没有兜住？

> **判据：把卡读成一个"没看过上一轮的人"——他能发现哪两条要求互相打架吗？**

### 原理 10 · 视觉决策必须交给人

导演**不得自行决定视觉表现**（几何形状、动画形式、配色、镜头感）。正确做法分三步：

```
① 列出带取舍说明的 A/B 方案    ② 人做出选择    ③ 贴出完整卡，等人确认下发
```

**⚠️ 第 ③ 步不可省。人选了方案 ≠ 授权整张卡。**

原因：**视觉要求无法用约束语言完整表达。** 导演自作主张写下的视觉指令，Worker 只会精确执行——**精确地错**。等你看到画面才发现，已经烧掉一整轮。

> 某卡的事故链条：导演自行选定"某种回到起点的运动方式" → 顺手写下"某元素全程跟随另一物体" → Worker 照做 → 人看到荒诞画面。
> **源头是导演没交出选择权。**

### 原理 11 · 下发闸门：不可逆动作必须先拿确认【教训】

**任何 `subagent(...)` / `send_message(...)` 之前，必须先拿到人的明确确认。**
流程固定两步，**不可合并到同一个回合**：

```
你：贴出【完整任务卡】+ 问"确认下发？回复 OK"
人：OK
你：才允许调用工具
```

**为什么：下发不可逆。** 卡一发出，Worker 就开始烧 token、改文件；卡里的每条约束**在下发那一刻冻结**，事后只能发修订卡，代价是整整一轮。**这个闸门是导演唯一的自我纠错机会——它自己写的卡，自己看不出问题。**

**已发生的事故**：导演给 A/B → 人选 A → 导演**立刻下发**。人的选择只覆盖了"视觉风格"一个维度，而卡里：
- 有一条验收标准是**恒真的**（Worker 什么都不做也能通过）
- **夹带了一个全新的子系统**这个卡外功能
- 两处视觉语义的冲突**没确认**

**这些都写于"人选 A"之后，人一次都没看到。**

**明确禁止**：
- ❌ 把"贴卡"和"调用工具"放在同一回合
- ❌ 把人做过的方案选择当成整卡授权
- ❌ 把"没回复"理解成默认同意
- ❌ 以"人要快""我很确定"为由跳过

### 原理 12 · 恒真的验收标准等于没写

**判据一句话：如果 Worker 什么都不做，这条标准会不会也通过？会通过的标准，等于没写。**

这类标准通常长这样——断言一个**在某个必经分支里必然被赋值的量**：

> **某卡实例（已匿名化）**：验收标准要求"判静止那一帧 `|v| < 阈值 × 0.1`"。
> 实测多种触发参数下，静止帧的速度分量**全是精确的 0.0000**。
> 因为源码里"把速度清零 + 进入静止态"**写在同一个分支内**（先清零，才轮到断言那一帧）——
> 判静止那一帧必然为零。所以"0 < 阈值"恒真，Worker 写一行 `assert(0 < 阈值)` 就"通过"。

**正确做法**：把断言移到**有不确定性的地方**。上例中真正值得测的是"静止前**过程**中是否有可见的异常滑动"（`|v| ≤ 阈值` 且单调不增），而不是静止那一瞬间的结果。

### 原理 13 · 一张卡只做一件事（原子性）

**每张卡只允许一个「可独立验收」的目标。** 夹带物要拆成独立的新卡：

| 夹带物 | 为什么必须拆 |
|---|---|
| 新子系统（顺带加个渲染层/音效/存档） | 出问题时**无法定位是哪一半** |
| 新交互维度（顺带支持滚轮缩放） | 验收标准互相干扰，失败原因被掩盖 |
| 无关重构（顺便整理渲染循环） | 破坏"增量修改"的可回滚性 |

**判据：如果这一卡失败了，你能不能一句话说清"失败的是哪个功能"？说不清就是不原子。**

> **某卡实例（已匿名化）**：目标本是"修复某个视觉表现"（纯视觉修复），却夹带了"新增一套运动过程的可视化"——一个自带采样、对象池、逐点材质、淡出、resize 处理的**全新子系统**，还带来 2 条验收标准。一旦失败，无法判断是原有视觉部分错了还是新子系统错了。

## 四、完整闭环与职责划分

```
人给意图
   │
   ① 导演出卡（无工具，纯协议产物）
   │     格式见 task-card-template.md，必须含「验证证据出口」
   │
   ② subagent(prompt = Worker 角色卡 + 任务卡, run_in_background: true)
   │     为什么塞 prompt 而不让它自己读文件：少一个失败点，可靠性优先
   │
   ③ Worker 在独立会话执行（写代码 → 起服务 → 自检 → 截图）
   │
   ④ 结算通知回流（只有通知头 + 收尾文本）
   │
   ⑤ 导演独立复核 ← 最容易省、也最不能省的一环
   │     · md5 逐字比对        · 静态事实核查（grep 零外部引用）
   │     · 结构核查（分支真的在）· 重跑 Worker 的脚本
   │     · 亲眼看交付的截图/画面
   │
   ├─ 通过 → ⑥ 出下一张卡 / send_message 续派
   └─ 不通过 → ⑥ 出「修订卡」，字段见 task-card-template.md
                     必须含「对上一轮未决问题的裁定」
```

| 环节 | 谁负责 | 为什么 |
|---|---|---|
| 需求拆解、任务卡质量 | 导演 | 卡的质量上限 = Worker 的产出上限 |
| 代码实现、自检、证据落盘 | Worker | 执行岗 |
| **独立复核、判定验收** | **导演** | **不重合的核查才有价值；只重复报告内容就是传声筒** |
| **画面好不好看** | **人** | 渲染结果目前只有人能判（这正是"截图校验 Worker"要解决的问题） |

## 五、决策树：复用 Worker 还是新开

```
需要变更？
  ├─ 同一画面/模块的迭代、修 bug、加细节
  │     → 复用（send_message）。它记得自己的实现，改得精准
  │
  ├─ 新画面的独立任务、与前面无关
  │     → 新开。干净上下文，不受历史实现干扰
  │
  ├─ 上一轮失败，且失败原因是它误解了需求
  │     → 新开。同一会话里它已形成错误理解，很难自纠
  │
  ├─ 上下文被长任务撑大、开始变迟钝
  │     → 新开，并在新卡里带必要现状摘要
  │
  └─ 需要另一种权限（工作区外写入、装依赖）
        → 新开（权限派生瞬间冻结，事后无法提权）
```

## 六、协议模板的关键字段（为什么必须有）

| 字段 | 解决的问题 |
|---|---|
| **目标** | 一句话说清达成什么，避免"优化一下"这类无法验收的表述 |
| **验收标准** | 每条都要能被 Worker 用代码/命令给出证据 |
| **涉及文件** | 说清可改范围，防止它顺手改无关文件 |
| **画面与时间轴 / 动效参数** | 把模糊需求量化，是导演的核心价值 |
| **不许改动的部分** | 划边界。**但不要写成"不许新建任何文件"** |
| **验证证据出口** | 保证证据可独立复核（见原理 5） |
| **预览端口** | 避免和已有服务冲突 |
| **修订卡的「对未决问题的裁定」** | **不置可否 = 让它下一轮重新猜，甚至把对的改错** |
| **修订卡的「先解除/调整的约束」** | 约束变了要明说，否则它不敢动 |

## 七、失败模式清单（遇到时对照）

| 症状 | 根因 | 处置 |
|---|---|---|
| Worker 报告"验证过了"但导演无法复核 | 证据落在临时目录 | 检查任务卡有没有写证据出口 |
| `curl` 曾经 200，现在连不上（`-102`） | 游离进程被回收 / 证据过期 | 导演自己重跑；服务改用受管后台作业 |
| Worker 说"环境问题，做不到" | 多半是权限被拒或约束自相矛盾 | 看它的「未决问题」；检查任务卡约束是否打架 |
| Worker 反复两轮同一个点做不对 | 卡有歧义，或它已形成错误理解 | 改卡重派；或新开 Worker |
| Worker 顺手重构了无关代码 | 「不许改动的部分」没写清 | 补边界；必要时回滚 |
| 导演上下文越来越长、开始变慢 | 结算通知累积 | 换新导演会话，靠协议 + 台账冷启动 |
| 派生 Worker 却写不了文件 | 父会话是 `read-only`（权限只能更窄） | 改用 `workspace-write` 会话当导演；`read-only` 不可改，需新开会话 |
| Worker 精确实现了荒诞的画面 | 卡里两条约束打架（新指令否定了历史裁定） | 按原理 9 做一致性检查；修卡重派，别怪 Worker |
| 画面/行为违反常识 | 卡里的视觉语义没写清（某元素"跟随"另一个元素，但没说什么情况下不跟） | 按原理 9 第 2 条追问"有谁在施力"；必要时按原理 10 交回人决策 |
| 验收标准验的是 Worker 刚写的变量 | 断言绑定了内部实现（白盒） | 改成黑盒行为断言 |
| 导演自行定下视觉表现，做完才发现不对 | 视觉决策没交给人 | 按原理 10 要求 A/B 方案；重做一轮的代价远大于问一句 |
| 卡里夹带了没人要的新功能 | 没做原子性检查 | 按原理 13 拆卡；"失败时能一句话说清是哪个功能错了吗" |
| 一条验收标准 Worker 不干活也能过 | 断言了必经分支里必然成立的量 | 按原理 12 问"什么都不做会不会也通过" |
| 人选了方案，导演立刻下发，人没看过整卡 | 缺下发闸门 | 按原理 11 强制两段式：贴卡 → 等人 OK → 才发 |
| 人提了反馈，但导演已经执行完了 | 下发不可逆 | 同原理 11；**闸门是唯一的预防手段，事后只能靠修订卡补救** |

## 八、进阶路线（基础闭环跑通后）

1. **第三只校验 Worker** —— 截图自动校验画面合规性，把"人看画面"这步自动化
2. **Git 插件** —— 成功自动提交、失败自动回滚，复刻版本迭代工作流
3. **替换编码模型** —— 复杂场景换更强的模型，**不改流水线架构**
4. **拓展案例** —— 换一个领域重跑一遍，验证协议本身可迁移

> 注意顺序：**先跑通基础闭环，再做模型替换与自动化调度。** 一上来就上自动化，会在还没理解隔离与回传边界时就被复杂度淹没。

## 九、一句话总纲

> **调度靠 Harness，思考靠 Model，记忆靠 Session，执行靠 Worker，
> 纪律靠协议，验收靠可复算的证据，判断靠人。**

### 三条不可省略的纪律（事故复盘浓缩）

1. **下发前必须确认**（原理 11）—— 不可逆动作，贴卡 → 等人 OK → 才发。
2. **一张卡只做一件事**（原理 13）—— 失败时能一句话说清是哪个功能错了吗。
3. **恒真的标准等于没写**（原理 12）—— Worker 什么都不做会不会也通过。

> 这三条的共性是：**它们拦的都是"事后无法补救"的错误。**
> 卡一旦下发，约束即冻结；功能一旦混在一起，失败无法归因。**闸门必须在前面。**
